# Plan a gated, privacy-safe SGR migration to MySQL

**Decision:** Migrate the first-delivery `cuentas`, `organizacion`, `agenda`, and `indicadores` slice only after human reconciliation, a local restore rehearsal, and verified access controls. Use the nine-entity, ten-FK proposed core in `docs/sgr-backend-mysql-mer.md`; Django's built-in `auth.User` is one of the nine, not an additional SGR table. This document is a **future execution plan**, not authorization to inspect records, connect to a database, run migrations, provision accounts, export data, or deploy. No implementation, import, MySQL connection, tests, backup, or remote work has occurred as part of this plan. [MER §§ “Proposed ER diagram”, “Approved first-release policies”; `docs/sgr-system-specification.md` §§ “Current local baseline vs delivery stages”, “Privacy and safety”.]

## Quick path: gates, not commands

1. **Prepare:** confirm data permission, source classification, local target, least-privilege access, clean repository hygiene, baseline schema, and an independently verified backup/restore rehearsal. Any missing approval is **no-go**.
2. **Reconcile and rehearse:** privately resolve identities, scoped owner/delegation links, catalog collisions and target weights; load only approved rows into an isolated, authorized local MySQL rehearsal. Failed checks or unresolved mandatory FKs block promotion.
3. **Cut over only on evidence:** compare restricted reconciliation totals with MySQL, exercise scoped Admin/ORM views and negative authorization cases, record restore point and owner sign-off, then separately authorize the production cutover. Keep the old source unchanged until explicit retention/disposition approval. Failure triggers a stop and restore decision, not a blind schema reversal.

The sequence below describes work **to be authorized later**. A running local service, installed driver, or passing documentation check alone never satisfies these gates. [MER §§ “Legacy-to-proposal mapping”, “Remaining pre-implementation validations”; [Django 6.1 migrations](https://docs.djangoproject.com/en/6.1/topics/migrations/).]

## Readiness from the authorized aggregate-only audit

The earlier separately authorized **read-only, in-memory** audit reported 10 persons, 6 delegations, 10 commitments, 33 nested items, 25 historical events and one period. These are source baselines, **not promised canonical import counts**. Seven persons have items and three have none. Six of those seven weight sets total 100%; the seventh needs review before any weighted score. All 33 items have a weight, positive numeric goal and nonnegative numeric progress; the period has full date endpoints, all ten commitment date pairs and 25 event dates have full parseable ISO dates. This does not establish unique catalog keys, approved period links, verified scores or valid scoped permissions. [Prior authorized aggregate-only audit; MER §§ “Stored attributes and integrity rules”, “Legacy-to-proposal mapping”.]

- Eight person-to-delegation name links have a single **candidate**; one is blank and one has no candidate. Seven commitment owner-name links have a candidate, three have none. Twenty-one historical actor-name links have a candidate, four have none. None of these candidate identities is human-confirmed. All ten territory labels have a delegation-name candidate, but **zero territory-derived FKs are verified**: resolve commitment scope independently of that label.
- Ten last historical states match their parent commitment status. Nine historical changes violate the **new** normal sequential-forward policy: six jumps forward, two backward and one repeated. Preserve all nine as ordered legacy facts, flag in the restricted reconciliation record, and do not retrofit new authorization rules onto historical events. Ten credential fields have recognizable hash-prefix *shape* only; neither valid login nor safe reuse follows. **Never import those hashes.**
- Record only aggregate exceptions in this shareable plan; the private resolution report holds source references, reasons, candidates and approved outcomes without entering Git, general Admin, logs, or public screenshots. If a previously observed count changes, freeze a new source snapshot under separate authorization and re-baseline rather than silently changing expected totals. ## Recovery and rollback boundary

**Before schema application:** operator proves an authorized isolated backup can be restored, checks both restored schema and aggregate data, records snapshot identity and recovery owner, and prevents concurrent source writes during the final comparison. Backup creation and rehearsal are future work requiring separate permission, not completed evidence here.

**If rehearsal or schema application fails:** stop, isolate the partial database and preserve diagnostic metadata without leaking data; restore the tested pre-change snapshot into an approved isolated target, verify schema/FKs and aggregate counts, then seek owner approval before retry. MySQL schema alterations are not transactionally reversible as a unit: do **not** assume rolling back a Python/Django transaction undoes DDL. A manual reverse migration is not a substitute for a tested restore. [Django 6.1 migrations](https://docs.djangoproject.com/en/6.1/topics/migrations/).]

**If cutover fails:** freeze new writes, retain the last known-good source and current MySQL snapshot for investigation, determine whether any post-cutover writes require separately approved reconciliation, restore the verified snapshot only under operator/data-owner authorization, and verify counts and login/scope isolation before reopening. Do not switch traffic back blindly or delete original records. Documentation rollback means removing this plan and `odd/tasks/sgr-mysql-migration-plan.md`; it does **not** restore a database or grant migration authority.
